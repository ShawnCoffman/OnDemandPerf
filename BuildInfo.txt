# Accepted Architecture — Current Prototype

Version 0.4.0 implements /run, /memory, and /disk, with Quick Analysis in the tray/window. RAM uses bounded managed buffers and verified copy/read/write passes. Disk uses aligned direct I/O, queue depth 1, latency metrics, a 528 MiB write-payload cap, and delete-on-close cleanup. CPU/RAM/disk stage limits are 18/11/22 seconds; work cancellation at 55 seconds reserves cleanup/report time before the tray termination deadline at 60 seconds. Runs may finish sooner when byte caps are reached. README.md documents implemented methodology and limitations; the detailed original plan below remains broader future scope.

OnDemand Perf starts at user sign-in and waits in the system tray. Startup must not collect inventory or run benchmarks. A user explicitly starts work from the tray or window; enterprise management can invoke the worker directly.

- C# / .NET 10 LTS, Windows Forms tray interface, unsafe code disabled.
- Version 0.3.0 uses deflate-v2: synchronized workers, single-thread and multithread passes, output verification, and variability reporting. CPU targets 12–15 seconds with an 18-second cooperative safety deadline. The eventual complete inventory/CPU/RAM/disk run targets 45 seconds and a 60-second overall deadline; this supersedes the older 30–90 second guidance below.
- Separate tray, worker executable, and shared core projects.
- First implementation: basic CPU/system inventory and a deterministic CPU compression test, JSON/text output, cancellation, deadlines, and overlap prevention.
- Version 0.2.0 adds friendly Windows product/edition/release/build, physical cores, system logical processors, OS-usable RAM, power source/plan, and a one-second pre-test CPU activity sample. Optional collection failures become warnings. BIOS/storage/DIMM inventory remains future work.
- Default prototype output is per-user `%LOCALAPPDATA%\OnDemandPerf\`; `/output` overrides it for managed worker execution. Machine-wide output policy remains a deployment decision.
- Keep 50 historical report pairs; rotate the log at 2 MiB with one backup.
- Prototype build uses the installed .NET 10 Desktop Runtime. Signed installer, runtime distribution, managed startup policy, and fleet rollout validation follow later.
- A helper script can register user sign-in startup. Building does not alter this computer's startup settings.
- Implement CPU first, then memory/storage, then expand inventory and deployment readiness. The older numbered phases below describe the broader scope, not the revised implementation order.

# OnDemand Perf — Project Build Plan

## Project Goal

Build a very small Windows application named **OnDemand Perf** that performs a fast hardware inventory and a handful of lightweight benchmark tests.

The application is intended for enterprise hardware validation and troubleshooting.

The focus is:

- Very small footprint
- Fast execution
- Minimal dependencies
- No internet requirement
- No third-party benchmark suites
- No installation requirement for the first version
- Easy to run manually or remotely
- Consistent and repeatable test results
- JSON-first output for later ingestion into databases, Power BI, GCP, Tanium, Intune, or other tools

This is not intended to compete with Cinebench, PCMark, CrystalDiskMark, PassMark, or other full benchmarking suites.

The goal is a **quick hardware performance snapshot** that can normally finish in roughly 30–90 seconds.

# Default Output Location

All output must be stored under:

`%LOCALAPPDATA%\OnDemandPerf\`

Directory structure:

```text
%LOCALAPPDATA%\OnDemandPerf\
│
├── Latest.json
├── Latest.txt
├── OnDemandPerf.log
│
└── Results\
    ├── 2026-09-24_191745.json
    ├── 2026-09-24_191745.txt
    └── ...
```

Every execution should:

1. Create the directory if it does not exist.
2. Generate a timestamped result.
3. Write the latest result to `Latest.json`.
4. Write a human-readable copy to `Latest.txt`.
5. Store a timestamped historical copy under `Results`.
6. Log execution details and errors to `OnDemandPerf.log`.

The benchmark should never silently fail.

# CPU Benchmark

Create a quick and deterministic CPU workload.

Preferred benchmark:

## Compression Benchmark

Generate or allocate a known in-memory dataset and repeatedly compress it.

Possible algorithms:

- Deflate
- GZip
- Brotli

Use a fixed test dataset and workload for every machine.

Measure:

- Input data size
- Total bytes processed
- Benchmark duration
- MB/s throughput

Preferred output:

```text
CPU Compression: 684.2 MB/s
```

The benchmark should run long enough to provide a stable result but short enough to remain a quick test.

Suggested duration:

Approximately 5–10 seconds.

Use all logical processors if practical.

---

# Optional CPU Secondary Test

Consider adding a second low-cost CPU benchmark such as:

- SHA-256 hashing
- AES encryption
- decompression

Example:

```text
SHA256 Throughput: 3,482 MB/s
```

This may be added after the compression test is working reliably.

Do not add generic synthetic scores.

---

# Memory Benchmark

Create a lightweight memory bandwidth test.

At minimum test:

- Sequential memory write
- Sequential memory read
- Memory copy

Use large memory buffers.

Suggested allocation:

256 MB to 1 GB depending on available RAM.

Avoid allocating so much memory that the application causes system pressure.

The application should dynamically reduce the test size on low-memory systems.

Measure:

```text
Memory Read: XX.X GB/s
Memory Write: XX.X GB/s
Memory Copy: XX.X GB/s
```

Prefer the memory copy result as the primary comparison metric.

The test should execute multiple passes and average the result to reduce noise.

Example:

```text
Memory Copy: 42.6 GB/s
```

Avoid claiming this represents raw theoretical DDR bandwidth.

It is an application-level memory throughput measurement.

---

# Storage Benchmark

Create a temporary benchmark file under:

`%LOCALAPPDATA%\OnDemandPerf\TestData\`

Delete temporary benchmark files after testing.

Do not benchmark using tiny cached files.

Use a sufficiently large file to reduce filesystem cache distortion.

Recommended initial size:

512 MB

Optionally:

1 GB

depending on available disk space.

---

# Sequential Disk Test

Measure:

- Sequential write throughput
- Sequential read throughput

Use large block sizes.

Suggested block size:

1 MB

Results:

```text
Sequential Read: 5,124 MB/s
Sequential Write: 4,378 MB/s
```

---

# Random Disk Test

Include a lightweight 4K random test if practical.

Measure:

- 4K random read
- 4K random write

Results may be represented as:

```text
Random Read: 392 MB/s
Random Write: 318 MB/s
```

or optionally IOPS:

```text
4K Random Read: 100,352 IOPS
```

For version 1, prioritize repeatability over maximum benchmark sophistication.

---

# Disk Safety Requirements

The storage test must:

- Never benchmark the entire physical disk destructively
- Never overwrite user files
- Only use application-created temporary files
- Check available free space before running
- Delete the test file when completed
- Attempt cleanup after failures
- Avoid running huge write workloads

The benchmark should intentionally remain lightweight to reduce SSD wear.

---

# Benchmark Repeatability

Each benchmark should have:

- Fixed workload
- Fixed test sizes where practical
- Fixed number of passes
- Stable timing method
- Clear units

Use a high-resolution timer such as:

`Stopwatch`

Ignore extremely short warm-up passes.

Consider performing:

```text
Warmup
Pass 1
Pass 2
Pass 3
Average
```

Store individual pass results in JSON even if the UI only shows the average.

---

# Environmental Data

Capture basic system state at test time.

Include:

- CPU utilization before benchmark
- RAM utilization before benchmark
- Available RAM
- Battery vs AC power
- Power plan if accessible
- Disk free space

This helps explain abnormal benchmark results.

Do not attempt to aggressively manipulate the system before testing.

# Error Handling

Failure of one component should not terminate the entire application.

Example:

If battery information fails:

```text
Battery:
Unavailable
```

Continue running benchmarks.

If random disk testing fails:

```text
Sequential Read: Complete
Sequential Write: Complete
Random Read: Failed
Random Write: Failed
```

Still create the JSON output.

Each test should contain a status such as:

```text
Success
Failed
Skipped
Unsupported
```

Include errors in JSON.

---

# Privilege Requirements

The application should run successfully as a normal Windows user whenever possible.

Do not require administrative rights simply to perform:

- CPU testing
- RAM testing
- storage testing
- standard system inventory

If certain hardware fields require elevation, mark them unavailable instead of forcing elevation.

Administrator mode may be added later for advanced diagnostics.

# Benchmark Philosophy

Do not generate arbitrary scores such as:

```text
Overall Score: 8742
```

Store real engineering measurements instead.

Prefer:

```text
CPU Compression: 684 MB/s
Memory Copy: 42.6 GB/s
NVMe Sequential Read: 5124 MB/s
NVMe Sequential Write: 4378 MB/s
```

This allows future comparisons without changing the meaning of historic results.

If normalized scores are ever created later, calculate them in the analytics/backend layer rather than inside the endpoint application.
